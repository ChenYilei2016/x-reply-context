# 0.15.5 通知互斥隐藏条件与性能复核

## 使用口径

通知标题栏固定展示「已回且已点」「仅已回」「整理列表」「自动整理」。前两项互斥，再次点击已选项关闭隐藏。

- **已回且已点**：沿用原口径，同一原帖、同一个人的文字与红心都有依据才隐藏。他人原帖/引用帖要求点赞本帖。
- **仅已回**：只要求有文字回复依据，不要求红心；已有红心的也包含。他人原帖/引用帖按已评论该原帖判断。
- 待确认、自我回复、自己原帖不因此隐藏。点赞/关注/转发通知仍由各自独立开关控制。
- 主动切换条件时应用一次；之后晚到的依据、新通知沿用手动整理或空闲 10 秒、阅读区下方 600px、一轮即停的规则。回复框内禁用筛选，保留阅读位置保护，不主动翻页。

使用单个 `notificationHideMode` 设置保存 `off / completed / replied`，避免两个开关同时为真。未保存新设置时兼容旧 `hideCompletedNotifications`；一旦选择新条件，以新设置为准，保存失败不切换。

## 验证与性能结论

- 74 项 Node 检查通过，包括互斥、再次点击关闭、保存失败、旧设置恢复、回复框暂停和晚到数据保护。
- 24 组接口/入口稳定性检查通过；本次不改变接收、分页、连续回复或存储写入链路。
- 本地浏览器已确认「文字已回/红心待确认」隐藏、「只有红心」保留，切回原条件后恢复；按钮节点与位置固定。
- 新条件只在现有卡片判断中增加常数开销，复用标签和筛选分类缓存，不新增后台队列、X 请求、定时器或存储全量读取。模式变化不清空标签分类缓存。
- 复核接收合批、后台优先队列、变更键写入、分类缓存和 DOM 更新链路：沿用 0.15.4 的保护与上限；没有因新条件增加存储规模或滚动扫描。
- [当前本地性能样本](performance-0.15.5.json)：用户/帖子/回复/红心各 10000 条，缓存预热后 100 条分类中位约 0.21ms，500 条红心合并约 0.74ms，单条热更新约 0.01ms。仅为 Node 中纯计算结果，不含 Chrome 消息传输、磁盘写入、DOM 渲染和 X 网络耗时。

剩余性能边界仍是后台冷启动恢复与帖子关系变化后的全量索引维护；没有为了新增条件改写数据库或扩大缓存。此前 0.15.4 的浏览器存储与反馈证据见[历史记录](0.15.4.md)，不冒充本次的真实 X 实测。本轮未操作真实账号的点赞、评论或关注。

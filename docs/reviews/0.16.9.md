# 0.16.9 · 保守界面优化与红心保留修复

本次分开处理两件事：界面优化保持功能与数据口径不变；红心保留规则按用户确认的方向修复。没有缩短历史保留时间、减少保存上限、丢弃待写队列、自动刷新页面或增加 X 请求。

## 界面优化

- 通知标题栏和回复工具栏读取实际 DOM 值，仅在属性确实变化时写入；弹窗、忙碌、错误、互斥切换和外部节点变化仍即时更新。
- 标题栏在同一次同步渲染中复用弹窗状态判断，先读布局再写控件，减少重复布局检查。
- 筛选器只复用同一次同步调用中已读取的卡片快照，不跨轮次缓存 DOM；新挂载、虚拟节点复用、账号和列变化仍重新核对。
- 不修改布局、阅读区保护、筛选条件、自动整理触发频率、组合发送或数据入库节奏。

## 红心问题与修复

确认的问题在保留阶段：原来所有 `liked:false` 浏览快照都与真实红心共用 10,000 条额度，按最近看到的时间淘汰。受控复现：先存 1 组回复和 1 条真实点赞，再浏览 10,000 条未点赞快照，没有取消操作，旧版变成 1 组回复、0 条红心；新版仍保留 1 组回复、1 条红心，总记录数仍为 10,000。[复现对照](like-retention-0.16.9.json)。

新规则：

1. 已确认点赞、明确点赞／取消回执、曾有正向证据后变为未点赞的记录优先保留；只有普通未点赞浏览快照时优先淘汰。旧的已点赞记录无需全库迁移即可获得优先级。
2. 原有时间先后校验继续保留，取消记录更新成后续未点赞快照后也不失去证据优先级。
3. 负快照被淘汰时，留下最多 20 个账号级时间保护项，随原元数据同事务保存；过期清理仍为 90 天。没有新建另一份无限增长的逐帖表。
4. 对已无逐帖记录、又早于被淘汰负快照的未知快照，保守忽略，避免旧正快照误恢复。普通同请求时间的分批可继续，明确取消的同时间旧快照仍受保护；新响应和有效新操作可正常更新。不同账号的保护相互隔离。

第 4 点意味着少量迟到且无法核实的旧快照可能保持待确认，后续正常浏览的新依据再补齐；不额外补查，也不根据“评论过”推断“点过赞”。保留超过 10,000 条真实互动证据或超过 90 天仍可能淘汰，不承诺无限历史。

截图中的“组文字回复”按原帖＋对方去重，“条红心”按具体帖子去重且仅计已点状态，历史获取范围也不同。这次没有读取用户真实数据库来核对每一笔差额，不能将全部差额都归因于上述问题；已经被旧版淘汰的记录不会凭空恢复。

## 验证和边界

- Node 测试 **100/100**，包括性能回归、保留优先级、取消校验、淘汰后旧响应、同批分段、账号隔离及 90 天清理。
- Chrome 本地受控编辑器 **35/35**，覆盖不重复写 DOM、输入、AI、草稿保护与原有操作。
- localhost 真实 IndexedDB **9/9**：旧记录迁入、单红心增量写入、冷重开、事务失败恢复，以及时间保护／证据优先级持久化。单次已知红心仍只写一条红心和元数据。[浏览器证据](render-retention-0.16.9.json)。
- 本轮没有操作真实 X 账号、发送／点赞或调用模型，也没有做数小时真实驻留的内存剖析。
- 没有修改待写队列容量或真正新数据的关联重建算法；持续写入异常导致的积压风险仍需单独处理，不能据此承诺长时间使用绝不会卡顿。

源码、README、安装包及原安装目录同步到 0.16.9。重载扩展并刷新 X 后生效；不需要清空历史，旧设置保留。本次未提交或推送 Git。
